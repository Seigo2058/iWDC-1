# เอกสารข้อกำหนด: การเชื่อมต่อ AI วิเคราะห์อาหาร

> เอกสารนี้แปลจากต้นฉบับภาษาญี่ปุ่น `connect-aisystem.md` หากเนื้อหาไม่ตรงกัน ให้ถือต้นฉบับภาษาญี่ปุ่นเป็นหลัก

**ผลิตภัณฑ์เป้าหมาย:** Point & Know (API วิเคราะห์อาหาร)
**การปรับปรุง:** สะท้อนการพัฒนาของ `ai/app/routers/food.py` (PR #3) และการเชื่อมต่อฝั่ง web (`dev/web-ai-integration`) response เมื่อไม่พบอาหารและ CORS ที่ฉบับเดิมระบุว่า "ยังไม่กำหนด" ได้ข้อสรุปจากการพัฒนาแล้ว

## 1. ความเป็นมาและวัตถุประสงค์

ส่งรูปภาพที่ยืนยันแล้วจากขั้นตอน ถ่ายภาพ → ครอบตัด → ยืนยัน (ขั้นตอนที่กำหนดไว้ใน `capture-tasks.md`) ไปยัง AI วิเคราะห์อาหาร เพื่อให้ระบุอาหารในภาพ แล้วรับชื่อ คำอธิบาย ส่วนประกอบ ข้อมูลโภชนาการ ฯลฯ เป็นภาษาอังกฤษ ไทย และญี่ปุ่น มาแสดงในแอป

API วิเคราะห์อาหารพัฒนาไว้ใน `ai/` (FastAPI) ของ repository นี้

| หัวข้อ | ตำแหน่ง |
| --- | --- |
| การพัฒนา endpoint | `ai/app/routers/food.py` (`POST /api/analyze-food`) |
| การระบุอาหาร | Google Gemini (`GEMINI_API_KEY`) |
| ข้อมูลอาหาร | Postgres ของ Supabase ตาราง `food_items` (`ai/app/db/models.py`) |
| วิธีจับคู่ | ค้นหา `food_items.name_en` ด้วยชื่อภาษาอังกฤษที่ Gemini ส่งกลับมา แบบตรงกันทุกตัวอักษรโดยไม่สนตัวพิมพ์เล็ก/ใหญ่ |

## 2. ตำแหน่งภายในแอป

| หัวข้อ | รายละเอียด |
| --- | --- |
| จังหวะที่เรียก | เมื่อกด "ยืนยันรูปภาพ (Decide Photo)" ใน `ConfirmStep` (หน้ายืนยัน) |
| ผู้เรียก | `web/lib/capture/submitPhoto.ts` |
| ข้อมูลที่ส่ง | รูปภาพสุดท้ายที่บีบอัดแล้วใน `ConfirmStep` (`finalImage` เป็น JPEG เสมอ) |
| การแสดงผลเมื่อสำเร็จ | `web/components/capture/ResultStep.tsx` หากมี 1 รายการ แสดงการ์ดข้อมูลอาหาร (`FoodDetail`) ทันที หากมีหลายรายการ แสดงรายการอาหาร (`FoodList`) → แตะเพื่อแสดงการ์ดข้อมูลอาหาร (3.3.1) |
| การแสดงผลเมื่อไม่พบ | หน้าจอไม่พบอาหาร (`web/components/capture/NotFoundStep.tsx` บทที่ 4) |

### 2.1 โครงสร้างการเชื่อมต่อ

เบราว์เซอร์จะไม่เรียก backend โดยตรง แต่เรียก `/api/analyze-food` ใน origin เดียวกัน แล้ว Next.js จะส่งต่อ request นั้นไปยัง backend ด้วย `rewrites` ใน `next.config.ts`

```
เบราว์เซอร์ ──POST /api/analyze-food──▶ Next.js (web, :3000)
                                          │ rewrites (ส่งต่อไปยัง AI_API_ORIGIN)
                                          ▼
                                 FastAPI (ai, :8000) ──▶ Gemini / Supabase
```

เหตุผลที่ใช้โครงสร้างนี้:
- เมื่อทดสอบจากสมาร์ทโฟนจริงผ่าน tunnel ของ cloudflared ใช้ tunnel ของ web เพียงเส้นเดียวก็พอ (`localhost:8000` จากมุมมองของเบราว์เซอร์จะชี้ไปที่ตัวสมาร์ทโฟนเอง จึงเข้าถึงโดยตรงไม่ได้)
- ไม่เกิด Mixed Content จากการเรียก backend แบบ HTTP จากหน้าเว็บ HTTPS
- เป็น origin เดียวกัน จึงไม่ได้รับผลกระทบจาก CORS

## 3. ข้อกำหนด API ที่เชื่อมต่อ

### 3.1 Endpoint

| หัวข้อ | รายละเอียด |
| --- | --- |
| Method | POST |
| URL ที่เรียกจากเบราว์เซอร์ | `/api/analyze-food` (origin เดียวกัน, คงที่) |
| ปลายทางที่ส่งต่อ | `${AI_API_ORIGIN}/api/analyze-food` โดย `AI_API_ORIGIN` เป็นตัวแปรสภาพแวดล้อมสำหรับฝั่งเซิร์ฟเวอร์เท่านั้น ตั้งค่าใน `web/.env.local` (ตัวอย่าง: `http://localhost:8000`) ไม่เปิดเผยให้เบราว์เซอร์ |
| คำอธิบาย | ส่งรูปภาพที่ครอบตัดแล้ว ให้ AI ระบุอาหาร แล้วดึงข้อมูลรายละเอียดจากฐานข้อมูล หากในรูปภาพเดียวมีอาหารหลายรายการ (เมนูอาหาร หรือโต๊ะที่มีจานหลายใบ) จะส่งกลับอาหารทั้งหมดที่ระบุได้ **ส่งได้เฉพาะรูปภาพ ไม่รองรับการส่งข้อความ** |

### 3.2 Request

- `Content-Type: multipart/form-data` — ให้เบราว์เซอร์ตั้งค่าอัตโนมัติ ไม่ตั้งค่าเองใน fetch
- Body: `FormData`

| ฟิลด์ | ชนิด | จำเป็น | คำอธิบาย |
| --- | --- | --- | --- |
| `file` | File | ○ | ไฟล์รูปภาพที่ครอบตัดแล้ว `Content-Type` ต้องขึ้นต้นด้วย `image/` แอปนี้ส่ง `photo.jpg` (`image/jpeg`) เสมอ |

```js
const formData = new FormData();
formData.append("file", new File([image], "photo.jpg", { type: "image/jpeg" }));
const response = await fetch("/api/analyze-food", {
  method: "POST",
  body: formData,
  // ไม่ต้องเพิ่ม header "Content-Type" เอง
});
```

**ข้อจำกัดของรูปภาพที่อัปโหลดได้:** ใช้การตั้งค่าการบีบอัดใน `web/components/capture/ConfirmStep.tsx` ต่อไป (`browser-image-compression`, `maxWidthOrHeight: 2000` / `maxSizeMB: 2`) หากจะเปลี่ยนการตั้งค่า ให้ตรวจสอบข้อกำหนดฝั่ง backend อีกครั้ง

### 3.3 Response (เมื่อระบุได้สำเร็จ, สถานะ 200)

`data` เป็น**อาร์เรย์ของออบเจ็กต์อาหาร** ซึ่งมีเฉพาะอาหารที่มีอยู่ใน DB (รูปภาพอาหาร 1 รายการจะมี 1 สมาชิก) อาหารที่ Gemini ระบุได้แต่ไม่มีใน DB จะไม่อยู่ในอาร์เรย์ และ response จะไม่ส่งชื่อกลับมาด้วย ลำดับในอาร์เรย์เป็นไปตามผลการค้นหาใน DB ไม่จำเป็นต้องตรงกับลำดับที่ Gemini ระบุได้

```json
{
  "status": "success",
  "message": "Found 2 food item(s).",
  "data": [
    {
      "food_id": 2,
      "name_en": "Tom Yum Goong",
      "name_th": "ต้มยำกุ้ง",
      "name_jp": "トムヤムクン",
      "description": { "en": "...", "th": "...", "jp": "..." },
      "ingredients": {
        "en": ["shrimp", "lemongrass", "..."],
        "th": ["กุ้ง", "ตะไคร้", "..."],
        "jp": ["エビ", "レモングラス", "..."]
      },
      "spicy_level": "Very Spicy",
      "audience": "Both",
      "country": "Thailand",
      "calories": "350 - 450",
      "protein": "10 - 15",
      "carbs": "50 - 60",
      "fat": "15 - 20",
      "how_to_eat": { "en": "...", "th": "...", "jp": "..." },
      "source_url": "https://en.wikipedia.org/wiki/Tom_yum",
      "image_url": ""
    },
    { "food_id": 5, "name_en": "Pad Krapow", "...": "..." }
  ]
}
```

| ฟิลด์ | ตัวอย่าง | การใช้งาน |
| --- | --- | --- |
| `status` | success | แสดงว่าทั้งการระบุและการจับคู่กับ DB สำเร็จ และ `data` มีอย่างน้อย 1 รายการ |
| `message` | Found 2 food item(s). | ข้อความสถานะของ response |
| `data[]` | อาร์เรย์ของออบเจ็กต์อาหาร | `data.*` ด้านล่างคือฟิลด์ของแต่ละสมาชิก |
| `data.food_id` | 2 | ID อาหารที่ไม่ซ้ำกันใน `food_items` |
| `data.name_en` / `name_th` / `name_jp` | Tom Yum Goong / ต้มยำกุ้ง / トムヤムクン | ชื่ออาหารภาษาอังกฤษ・ไทย・ญี่ปุ่น |
| `data.description` | `{en, th, jp}` | คำอธิบายอาหาร 3 ภาษา |
| `data.ingredients` | `{en, th, jp}` (อาร์เรย์สตริงของแต่ละภาษา) | ส่วนประกอบหลัก frontend รองรับทั้งสองรูปแบบ เพื่อให้แสดงผลได้แม้ได้รับอาร์เรย์ภาษาอังกฤษอย่างเดียวตามข้อกำหนดเดิม |
| `data.spicy_level` | Very Spicy | ระดับความเผ็ด **มี 4 แบบ: `No Spicy` / `Low Spicy` / `Medium Spicy` / `Very Spicy`** ป้ายชื่อ 3 ภาษาสำหรับแสดงผลเตรียมไว้ฝั่ง frontend |
| `data.audience` | Both | กลุ่มที่เหมาะสม ค่าใน DB คือ `Adult` (ผู้ใหญ่) / `Both` (ผู้ใหญ่และเด็ก) แสดงในส่วน "Suitable for" ของข้อมูลอาหารเป็นป้ายสีเทาแยกตามกลุ่ม ("ผู้ใหญ่", "เด็ก", `Both` แสดงทั้งสอง) ค่าที่ไม่รู้จักจะแสดงตามเดิม |
| `data.country` | Thailand | ประเทศของอาหาร (ชื่อภาษาอังกฤษ ค่าใน DB คือ `Thailand` / `Japan`) แสดงในส่วน "COUNTRY (ประเทศ)" ของข้อมูลอาหารเป็นชื่อประเทศในภาษาที่แสดง (`Intl.DisplayNames`) |
| `data.calories` | "350 - 450" | แคลอรี (kcal, ค่าโดยประมาณต่อหนึ่งมื้อ) คอลัมน์ DB `calories_kcal` (TEXT) **ส่งกลับเป็นช่วงค่าในรูปแบบข้อความ** ฝั่งหน้าเว็บจัดรูปแบบเป็น "350–450" เพื่อแสดงผล และแสดงได้แม้จะได้รับค่าเป็นตัวเลข |
| `data.protein` | "10 - 15" | ปริมาณโปรตีน (g, ค่าโดยประมาณต่อหนึ่งมื้อ) คอลัมน์ DB `protein_g` (TEXT รูปแบบเดียวกับ `calories`) |
| `data.carbs` | "50 - 60" | ปริมาณคาร์โบไฮเดรต (g, ค่าโดยประมาณต่อหนึ่งมื้อ) คอลัมน์ DB `carbohydrate_g` (TEXT รูปแบบเดียวกับ `calories`) |
| `data.fat` | "15 - 20" | ปริมาณไขมัน (g, ค่าโดยประมาณต่อหนึ่งมื้อ) คอลัมน์ DB `fat_g` (TEXT รูปแบบเดียวกับ `calories`) |
| `data.how_to_eat` | `{en, th, jp}` | วิธีรับประทานอาหาร 3 ภาษา |
| `data.source_url` | https://... | URL แหล่งที่มาของข้อมูลอาหาร (เฉพาะแหล่งภาษาอังกฤษ) |
| `data.image_url` | (อาจเป็นสตริงว่าง) | URL รูปภาพอ้างอิงของอาหาร ใช้สำหรับ "ภาพอ้างอิง" ในการ์ดข้อมูลอาหาร และภาพย่อในรายการอาหาร |

> `detected_name` (ชื่อภาษาอังกฤษที่ระบุได้ 1 ชื่อ) และรูปแบบที่ `data` เป็นออบเจ็กต์เดี่ยวตามข้อกำหนดเดิมถูกยกเลิกแล้ว frontend รองรับเฉพาะรูปแบบอาร์เรย์

#### 3.3.1 การแสดงอาหารหลายรายการ (frontend)

| จำนวนใน `data` | การแสดงผล |
| --- | --- |
| 1 รายการ | แสดงการ์ดข้อมูลอาหารทันทีเหมือนเดิม (แสดงรูปภาพที่ผู้ใช้ถ่ายด้วย) |
| 2 รายการขึ้นไป | แสดงรายการ "พบอาหาร N รายการ" แต่ละแถวมีภาพย่อจากภาพอ้างอิง・ชื่ออาหาร・คำอธิบาย (ไม่เกิน 2 บรรทัด)・ระดับความเผ็ด เมื่อแตะจะแสดงการ์ดข้อมูลของอาหารนั้น และกลับไปที่รายการด้วย "กลับไปที่รายการ" (คงตำแหน่งการเลื่อนของรายการไว้) รูปภาพของผู้ใช้เป็นภาพที่มีอาหารหลายรายการ จึงแสดงเฉพาะในรายการ ไม่แสดงในการ์ดข้อมูลอาหารแต่ละรายการ |

### 3.4 Response (ระบุได้แต่ไม่มีข้อมูลใน DB, สถานะ 200)

ในการพัฒนาของ `ai/app/routers/food.py` **จะคืนค่า HTTP 200 โดยตั้ง `status` เป็น `"partial_success"` และ `data` เป็นอาร์เรย์ว่าง** ชื่อภาษาอังกฤษที่ระบุได้จะอยู่ใน `detected_names`

```json
{
  "status": "partial_success",
  "message": "Food recognized, but details are not in our database yet.",
  "detected_names": ["Pad Krapow"],
  "data": []
}
```

> ข้อกำหนดฉบับเดิม (คำตอบของบทที่ 4 เดิม) ระบุว่า "เตรียม status code เฉพาะ" แต่การพัฒนาเป็นไปตามรูปแบบข้างต้น **frontend ปรับให้ตรงกับการพัฒนาแล้ว** หากในอนาคตเปลี่ยน backend ให้ใช้ status code เฉพาะ ต้องเปลี่ยนการตัดสินใน `submitPhoto.ts` ด้วย

### 3.4.1 Response (ระบุอาหารไม่ได้เลยแม้แต่รายการเดียว, สถานะ 200)

หาก Gemini ส่งอาร์เรย์ว่างกลับมา จะคืนค่าโดยไม่มี `data` frontend จะไปยังหน้าจอไม่พบอาหารเช่นเดียวกับ 3.4

```json
{
  "status": "fail",
  "message": "No recognizable food detected."
}
```

### 3.5 ข้อผิดพลาด

| สถานะ | ต้นทาง | ความหมาย | การจัดการของ frontend |
| --- | --- | --- | --- |
| 400 | backend | ไฟล์ที่อัปโหลดไม่ใช่รูปภาพ | ข้อความวิเคราะห์ล้มเหลว |
| 422 | backend | body ไม่มี `file` | ข้อความวิเคราะห์ล้มเหลว |
| 429 | backend | โมเดล Gemini ทั้งหมดที่ตั้งค่าไว้ใช้โควตา (จำนวน request สูงสุด) ครบแล้ว (7.1.1) | ข้อความวิเคราะห์ล้มเหลว |
| 503 | backend | โมเดลที่ใช้ได้ทั้งหมดมีผู้ใช้หนาแน่น・ไม่ตอบสนอง (รวมกรณีที่บางโมเดลใช้โควตาครบแล้ว) (7.1.1) | ข้อความวิเคราะห์ล้มเหลว |
| 500 | backend | Gemini ประมวลผลล้มเหลว หรือ DB เกิดข้อผิดพลาด | ข้อความวิเคราะห์ล้มเหลว |
| 500 | Next.js | backend ไม่ได้ทำงาน／เข้าถึงไม่ได้ (ส่งต่อไม่สำเร็จ) | ข้อความวิเคราะห์ล้มเหลว |
| 404 | Next.js / backend | ไม่ได้ตั้งค่า `AI_API_ORIGIN` หรือปลายทางไม่มี `/api/analyze-food` | ข้อความข้อผิดพลาดการตั้งค่า |

## 4. หน้าจอเมื่อไม่พบอาหาร

เมื่อไม่พบอาหาร จะแสดง `NotFoundStep` และเสนอการทำงานต่อไปนี้ (พัฒนาแล้ว)

| คำในข้อกำหนด | การพัฒนาในแอปนี้ |
| --- | --- |
| กลับไปที่แกลเลอรี | กลับไปที่หน้าหลัก (`/[lang]`) |
| ถ่ายรูป | เริ่มใหม่จากขั้นตอนถ่ายภาพ (`CaptureStep`) |
| แก้ไขรูปภาพอีกครั้ง | กลับไปที่ขั้นตอนครอบตัด (`CropStep`) (เก็บ `rawImage` ไว้) |

แอปนี้ไม่มีหน้าจอที่เทียบเท่า "แกลเลอรี" จึงตีความเป็นหน้าหลักแทน

## 5. ประเด็นที่ยังไม่ได้ข้อสรุป

1. **origin ของ backend ในสภาพแวดล้อม production/ทดสอบ** — ค่าที่จะตั้งใน `AI_API_ORIGIN` สำหรับการพัฒนาในเครื่องคือ `http://localhost:8000`
2. **เวลาประมวลผลการวิเคราะห์ด้วย AI・เกณฑ์ timeout** — ฝั่ง frontend ตั้ง timeout ชั่วคราวไว้ 30 วินาที
3. **จะเปลี่ยนวิธีคืนค่าเมื่อไม่พบอาหารให้เป็น status code เฉพาะตามข้อกำหนดหรือไม่** — ตกลงกับ backend ว่าจะใช้การพัฒนาปัจจุบัน (3.4) ต่อไปได้หรือไม่

## 6. แนวทางการพัฒนา frontend

- เบราว์เซอร์เรียก `/api/analyze-food` ใน origin เดียวกัน และส่งต่อไปยัง `AI_API_ORIGIN` ด้วย `rewrites` ใน `next.config.ts` ไม่เปิดเผย URL ของ backend ให้เบราว์เซอร์
- เมื่อไม่ได้ตั้งค่า `AI_API_ORIGIN` Next.js จะแสดงคำเตือนตอนเริ่มทำงาน และไม่ลงทะเบียนการส่งต่อ (request จะได้ 404)
- ไฟล์ที่ส่งเป็น JPEG เสมอ (ผลการบีบอัดจาก `ConfirmStep`) ไม่เปลี่ยนการตั้งค่าการบีบอัด
- เตรียม map แปลง `lang` (`"en"` | `"ja"` | `"th"`) → คำต่อท้ายภาษาของ API (`"en"` | `"jp"` | `"th"`) (ตีความ `ja` ของแอปนี้เป็น `jp` เฉพาะส่วนที่ติดต่อกับ API นี้เท่านั้น ไม่เปลี่ยนรหัสภาษาของทั้งแอปหรือโครงสร้าง URL `/ja`)
- ค่า 4 ค่าของ `spicy_level` มีช่องว่างอยู่ในค่า จึงแปลงเป็น slug (`none` / `low` / `medium` / `very`) เพื่อใช้อ้างอิงคีย์ i18n
- การแยกกรณีของ response:
  - 200 และ `status: "success"` (`data` เป็นอาร์เรย์ และมีอาหารที่รูปแบบถูกต้องอย่างน้อย 1 รายการ) → 1 รายการแสดงการ์ดข้อมูลอาหาร หลายรายการแสดงรายการอาหาร (3.3.1) ทิ้งสมาชิกที่รูปแบบผิดพลาด และแสดงเฉพาะส่วนที่เหลือ
  - 200 และกรณีอื่น (`partial_success` / `fail` ฯลฯ) → หน้าจอไม่พบอาหาร
  - 404 → ข้อผิดพลาดการตั้งค่า (อยู่ที่หน้ายืนยันต่อ)
  - ไม่ใช่ 200 กรณีอื่น → วิเคราะห์ล้มเหลว (อยู่ที่หน้ายืนยันต่อ และลองใหม่ได้ด้วยปุ่มยืนยัน)
  - การสื่อสารล้มเหลว・timeout → ข้อความข้อผิดพลาดของแต่ละกรณี (อยู่ที่หน้ายืนยันต่อ)
- ระหว่างที่ AI ประมวลผล ให้แสดง "กำลังวิเคราะห์อาหาร..."

## 7. ขั้นตอนการเริ่มทำงานในเครื่อง

### 7.1 backend (`ai/`)

1. กรอกข้อมูลต่อไปนี้ใน `ai/.env` (อยู่ใน `.gitignore`)
   - `DATABASE_URL` — URI ของ "Session pooler" จาก "Connect" มุมขวาบนของแดชบอร์ด Supabase เปลี่ยน `postgresql://` ที่ขึ้นต้นเป็น `postgresql+asyncpg://` (ไม่ใช้ Transaction pooler พอร์ต 6543 เพราะไม่เข้ากับ asyncpg)
   - `GEMINI_API_KEY` — API key ที่ออกจาก Google AI Studio
2. เริ่มทำงาน (เพื่อให้โหลด `.env` ต้องรันในไดเรกทอรี `ai/` เสมอ)

```bash
cd ai
python3 -m venv .venv          # ครั้งแรกเท่านั้น
.venv/bin/pip install -r requirements.txt   # ครั้งแรก・เมื่อเพิ่ม dependency
.venv/bin/uvicorn app.main:app --reload --port 8000
```

หากเปิดเอกสาร API ที่ `http://localhost:8000/docs` ได้ ถือว่าเริ่มทำงานสำเร็จ

**เมื่อเปลี่ยน `ai/.env` ให้รีสตาร์ท backend** `--reload` เฝ้าดูเฉพาะไฟล์ `.py` ส่วนตัวแปรสภาพแวดล้อม เช่น API key จะถูกโหลดเฉพาะตอนเริ่มทำงานเท่านั้น

#### 7.1.1 การสลับโมเดล Gemini อัตโนมัติ

โควตาฟรีของ Gemini จำกัดจำนวน request ต่อโมเดล (ตัวอย่าง: 20 ครั้งต่อวันต่อโมเดล) และบางครั้งโมเดลก็มีผู้ใช้หนาแน่นจนไม่ตอบสนอง `ai/app/services/gemini.py` จะส่ง request เดิมซ้ำด้วยโมเดลถัดไป เมื่อโมเดลใดใช้งานไม่ได้ในขณะนั้น (ตามตารางด้านล่าง) ทั้งการวิเคราะห์อาหารและรายละเอียดวัตถุดิบใช้กลไกนี้

| หัวข้อ | รายละเอียด |
| --- | --- |
| ลำดับที่ลอง | ตามลำดับใน `GEMINI_MODELS` (คั่นด้วยจุลภาค) ของ `ai/.env` การตั้งค่าปัจจุบันคือ **Flash ใหม่→เก่า แล้ว Pro ใหม่→เก่า**: `gemini-3.8-flash` → `gemini-3.7-flash` → `gemini-3.6-flash` → `gemini-3.5-flash` → `gemini-3-flash-preview` → `gemini-3.1-pro-preview` เมื่อเปลี่ยนแล้วให้รีสตาร์ท |
| เมื่อไม่มี `GEMINI_MODELS` | ลำดับเริ่มต้นในโค้ด (`DEFAULT_MODELS`): `gemini-3.6-flash` → `3.7-flash` → `3.8-flash` → `3.5-flash` → `3-flash-preview` → `3.1-flash-lite` → `3.5-flash-lite` |
| 429 (ใช้โควตาเกิน) | ไปยังโมเดลถัดไป หากเป็นขีดจำกัดรายวัน จะลองใหม่หลังจาก 1 ชั่วโมง หากเป็นขีดจำกัดต่อนาที จะลองใหม่หลังเวลารอที่ Gemini กำหนด (`retryDelay`) การเรียกที่ล้มเหลวด้วย 429 ไม่นับรวมในโควตา |
| 503 (ผู้ใช้หนาแน่น)／ไม่ตอบสนองภายใน 12 วินาที | ไปยังโมเดลถัดไป และลองโมเดลนั้นใหม่หลังจาก 60 วินาที การตอบสนองปกติใช้เวลา 1〜6 วินาที ค่า 12 วินาทีกำหนดไว้เพื่อให้แม้จะรอโมเดลแรกจนหมดเวลา โมเดลที่สองก็ยังทันก่อน timeout ของ frontend (การวิเคราะห์อาหาร 30 วินาที・รายละเอียดวัตถุดิบ 20 วินาที) |
| 404 (ยุติการให้บริการ) | ไปยังโมเดลถัดไป และไม่ใช้โมเดลนั้นจนกว่าจะรีสตาร์ท backend |
| ข้อผิดพลาดอื่น ๆ | ไม่สลับโมเดล คืนค่าข้อผิดพลาดตามเดิม (500) |
| เมื่อใช้ไม่ได้ทั้งหมด | หากทั้งหมดใช้โควตาเกิน คืนค่า **429** หากมีกรณีผู้ใช้หนาแน่น・ไม่ตอบสนองรวมอยู่ด้วย คืนค่า **503** (3.5) ปัจจุบัน frontend แสดงทั้งสองกรณีเหมือน "วิเคราะห์ล้มเหลว" |
| การเก็บสถานะ | เก็บในหน่วยความจำของ backend เท่านั้น เมื่อรีสตาร์ทจะถูกรีเซ็ต และเริ่มลองใหม่จากโมเดลแรก |

สถานะของแต่ละโมเดลที่ตรวจสอบเมื่อ 2026-09-13:

| โมเดล | สถานะ |
| --- | --- |
| `gemini-3.8-flash` | ตอบสนองได้ แต่เนื่องจากเป็นรุ่นล่าสุดจึงมีผู้ใช้หนาแน่นได้ง่าย เคยได้ 503 (รอนาน 36 วินาที) และเคยไม่ตอบสนองภายใน 12 วินาทีในการวิเคราะห์รูปภาพ |
| `gemini-3.7-flash` / `3.6-flash` / `3.5-flash` / `3-flash-preview` | ตอบสนองได้ |
| `gemini-3.1-pro-preview` | กับ API key นี้ (โควตาฟรี) ได้ 429 ตั้งแต่ request แรก คาดว่าใช้ Pro ไม่ได้ในโควตาฟรี วางไว้ท้ายสุดเป็นตัวสำรองเผื่อเปลี่ยนเป็นแผนแบบเสียเงิน |
| `gemini-2.5-flash` / `2.5-flash-lite` / `2.5-pro` | ยุติการให้บริการสำหรับผู้ใช้ใหม่ (404) จึงไม่ได้ใส่ไว้ |
| `gemini-flash-latest` / `gemini-pro-latest` | เป็นชื่อแฝงที่ชี้ไปยังโมเดลเฉพาะ ใช้โควตาร่วมกับโมเดลจริง จึงไม่ได้ใส่ไว้ |
| `gemini-3.1-pro-preview-customtools` | เป็นโมเดลแยกย่อยสำหรับ custom tools จึงไม่ได้ใส่ไว้ |

โมเดลที่ตอบสนองจะแสดงในล็อกของ backend เป็น `[GEMINI] Answered by <ชื่อโมเดล>`

### 7.2 web (`web/`)

1. ตั้งค่า `AI_API_ORIGIN=http://localhost:8000` ใน `web/.env.local` (`next.config.ts` อ่านค่าตอนเริ่มทำงาน หากเปลี่ยนให้รีสตาร์ท dev server)
2. เริ่มทำงานด้วย `npm run dev` หากทดสอบบนสมาร์ทโฟนจริง เปิดเผยเฉพาะ dev server ของ web ผ่าน cloudflared ก็พอ

## 8. รายการตรวจสอบการเชื่อมต่อฝั่ง frontend

- จากเบราว์เซอร์ POST ไปยัง `/api/analyze-food` ใน origin เดียวกัน
- append รูปภาพที่ครอบตัดแล้วลงใน `FormData` ด้วยชื่อฟิลด์ `"file"`
- ไม่ตั้งค่า header `"Content-Type"` เอง
- แสดง `data` (อาร์เรย์) เฉพาะเมื่อ `status: "success"` เท่านั้น 1 รายการแสดงการ์ดข้อมูลอาหาร หลายรายการแสดงรายการอาหาร
- `status: "partial_success"` (`data: []`) และ `status: "fail"` ให้ไปยังหน้าจอไม่พบอาหาร
- แปลงค่า 4 ค่าของ `spicy_level` เป็นป้ายชื่อ 3 ภาษาเพื่อแสดงผล
- แสดงข้อมูลโภชนาการ (calories/protein/carbs/fat) เป็น "ค่าโดยประมาณต่อหนึ่งมื้อ"
- 404 เป็นข้อผิดพลาดการตั้งค่า ส่วนไม่ใช่ 200 กรณีอื่น・การสื่อสารล้มเหลว・timeout ให้แสดงข้อผิดพลาดที่หน้ายืนยันและลองใหม่ได้
- ตั้งค่า URL ของ backend ด้วย `AI_API_ORIGIN` (ฝั่งเซิร์ฟเวอร์) ไม่เขียนไว้ในโค้ดหรือตัวแปรสภาพแวดล้อมสำหรับเบราว์เซอร์
