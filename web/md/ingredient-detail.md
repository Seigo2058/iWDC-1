# 食材詳細API連携 要件定義書

**対象プロダクト:** Point & Know（食材詳細API）
**前提:** `ai/app/routers/food.py` の `POST /api/ingredient-detail`（backend 実装済み）。料理解析API（`connect-aisystem.md`）の接続構成をそのまま使う。

## 1. 背景・目的

料理データカード（`FoodDetail`）の「主な材料」に並ぶ食材をユーザーがタップしたとき、その食材が何なのか（説明）と何から作られているのか（原材料）をポップアップで表示する。

データベースの容量を節約するため、この機能は**データベースを使わず、AI（Gemini）がリクエストのたびに説明文を生成・翻訳する**。そのため、応答に数秒かかり、内容が毎回同じとは限らない。

## 2. アプリ内の位置づけ

| 項目 | 内容 |
| --- | --- |
| 呼び出しタイミング | 料理データカードの「主な材料」で食材のボタンを押したとき |
| 呼び出し元 | 新規の `web/lib/ingredient/fetchIngredientDetail.ts`（7章） |
| 表示 | 食材詳細モーダル（新規の `web/components/capture/IngredientDetailModal.tsx`、4章） |
| 対象画面 | 1品のときの料理データカード、複数品のときの一覧からタップした料理データカードの両方（`FoodDetail` は共通） |
| 保存 | サーバー・Local Storage には保存しない。同じ画面を開いている間だけメモリにキャッシュする（6章） |

### 2.1 接続構成

backend の仕様上のURLは `http://localhost:8000/api/ingredient-detail` だが、**ブラウザからは直接呼ばず、料理解析APIと同じく同一オリジンの `/api/ingredient-detail` を呼び、`next.config.ts` の `rewrites` で `AI_API_ORIGIN` に中継する**（`connect-aisystem.md` 2.1 と同じ理由: スマホ実機からのトンネルが1本で済む、Mixed Content を避ける、CORS の影響を受けない）。

```
ブラウザ ──POST /api/ingredient-detail──▶ Next.js (web, :3000)
                                            │ rewrites（AI_API_ORIGIN へ転送）
                                            ▼
                                   FastAPI (ai, :8000) ──▶ Gemini
```

現状の `rewrites` は `/api/analyze-food` だけなので、`/api/ingredient-detail` の中継を追加する。

## 3. 連携API仕様

### 3.1 エンドポイント

| 項目 | 内容 |
| --- | --- |
| メソッド | POST |
| ブラウザから呼ぶURL | `/api/ingredient-detail`（同一オリジン、固定） |
| 転送先 | `${AI_API_ORIGIN}/api/ingredient-detail` |
| Content-Type | `application/json`（料理解析APIと違い、FormData ではない） |

### 3.2 リクエスト

```json
{
  "ingredient": "Katsuobushi (Bonito flakes)",
  "language": "jp"
}
```

| フィールド | 型 | 必須 | 内容 |
| --- | --- | --- | --- |
| `ingredient` | string | ○ | ユーザーがタップした食材の名前。**画面に表示している表記（現在の言語の食材名）をそのまま送る**（理由は下記） |
| `language` | `"en"` / `"jp"` / `"th"` | ○ | 現在アプリで選択されている言語。本アプリの `ja` は `jp` に読み替える（既存の `toApiLang()` を使う） |

**`ingredient` に表示中の表記を送る理由:** `food_items.ingredients` の各言語の配列は、同じ位置に同じ食材が並ぶことが保証されていない（翻訳が無い言語は英語で代替表示している）。そのため、タップした表記から英語名を確実に引けない。AIは日本語・タイ語の食材名も理解でき、2026-09-13 の確認では `"ingredient": "ナンプラー", "language": "th"` でタイ語の正しい説明が返った。

### 3.3 レスポンス（成功時、ステータス200）

```json
{
  "status": "success",
  "data": {
    "what_is_it": "鰹の肉を加熱してから乾燥させた日本の保存食品です。出汁をとったり、トッピングとして使われます。",
    "made_of": "鰹（カツオ）"
  }
}
```

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `status` | `"success"` | 生成に成功したことを示す。backend は成功時以外に200を返さない |
| `data.what_is_it` | string | 食材の短い説明（1〜2文）。`language` で指定した言語 |
| `data.made_of` | string | 原材料を並べた短い文字列。`language` で指定した言語 |

**注意:** `data` の中身は Gemini の出力をそのままJSONとして読んだもので、backend はキーや型を検証していない。キーが欠けたり、文字列以外が入ったりする可能性があるため、フロントで検証する（5章）。

### 3.4 backend が返すエラー

| ステータス | 発生条件 | body |
| --- | --- | --- |
| 422 | `ingredient` / `language` が無い、JSONとして読めない（FastAPI の検証） | `{"detail": [...]}` |
| 429 | 設定したすべての Gemini モデルが利用枠に達している（3.6） | `{"detail": "AI request limit reached for all models. ..."}` |
| 503 | 使えるモデルがすべて混雑・応答なし（3.6） | `{"detail": "AI models are busy right now. ..."}` |
| 500 | Gemini の呼び出し失敗、Gemini の出力がJSONとして読めない | `{"detail": "AI Processing Error: ..."}` |
| 500 | backend が起動していない／到達できない（Next.js の中継失敗） | Next.js のエラー |
| 404 | `AI_API_ORIGIN` が未設定、または中継先に `/api/ingredient-detail` が無い | Next.js の404 |

`detail` には内部のエラー文字列が入るため、**画面には表示しない**。

### 3.5 応答時間

2026-09-13 のローカル環境での実測は **約5〜6秒**（Gemini による生成時間がほぼすべて）。数秒待たせる前提でUIを作る（4.3）。

### 3.6 AI の利用枠

2026-09-13 の確認では、Gemini API は無料枠で **1モデルあたり1日20リクエスト**（`gemini-3.6-flash`）に制限されている。この枠は料理解析（`/api/analyze-food`）と食材詳細で共有する。

あるモデルが上限に達した・混雑している・8秒以内に応答しない場合、backend は自動で次のモデルに切り替える（`connect-aisystem.md` 7.1.1）。すべてのモデルが使えないときだけ **429**（すべて上限）または **503**（混雑を含む）を返し、フロントではどちらも「生成失敗」（5.2）として表示される。キャッシュと同時リクエストの共有（5.1・6章）はこの枠を節約するためでもある。

## 4. 画面仕様

### 4.1 食材ボタン

- 料理データカードの「主な材料」のチップ（現在は `<li>` の表示のみ）を、押せるボタンにする。見た目は現在のチップを保ち、押せることが分かる程度の変化（ホバー時の背景色、カーソル）を付ける。
- 「主な材料」の見出しの下に「食材をタップすると説明を表示します」の補足を1行添える。
- アレルギー情報（`allergens`）のチップは今回の対象外（押せないまま）。

### 4.2 食材詳細モーダル

| 要素 | 内容 |
| --- | --- |
| タイトル | タップした食材名（ボタンの表記と同じ） |
| 「どんな食材？」 | `data.what_is_it` |
| 「原材料」 | `data.made_of`。空のときは見出しごと出さない |
| 注意書き | 「AIが生成した説明です。正確でない場合があります。アレルギーの判断には使わず、必ずお店に確認してください。」を常に表示する |
| 閉じる | 右上の閉じるボタン、背景（オーバーレイ）のタップ、Escキーのいずれでも閉じる |

- スマホではボトムシート（画面下から出るパネル）、幅の広い画面では中央のダイアログとして表示する。
- ネイティブの `<dialog>` 要素（`showModal()`）を使い、開いている間は背面を操作できず、フォーカスがモーダル内に留まるようにする。閉じたらフォーカスを押した食材ボタンに戻す。
- 本文は React のテキストとして描画する（HTMLとして解釈しない）。

**注意書きを必須にする理由:** 「原材料」はアレルギー対応のユーザーが判断材料にしやすい情報だが、AIの生成結果であり、実際の料理で使われている原材料とは限らない。

### 4.3 状態と表示

```
[食材ボタンを押す] → 読み込み中 ──成功──▶ 説明を表示
                         │
                         └──失敗──▶ エラー表示 ──[もう一度試す]──▶ 読み込み中
```

| 状態 | 表示 |
| --- | --- |
| 読み込み中 | タイトル（食材名）は即座に表示し、本文の位置にスケルトン（灰色の帯）と「説明を生成しています...」を出す。閉じるボタンは押せる |
| 成功 | 4.2 の各要素 |
| 失敗 | エラーメッセージ（5章）と「もう一度試す」ボタン。閉じるボタンは押せる |

## 5. エラー処理

### 5.1 方針

- エラーは**モーダルの中だけで表示**し、料理データカードや撮影フローには影響させない（食材詳細は補足情報で、失敗しても料理の情報は見られるため）。
- **自動リトライはしない**。AI の呼び出しには費用と時間がかかるため、再試行はユーザーが「もう一度試す」を押したときだけ行う。
- **失敗した結果はキャッシュしない**（6章）。モーダルを閉じて同じ食材を押し直すと、改めてリクエストする。
- 読み込み中にモーダルを閉じた、または別の食材を開いた場合は、後から返ってきた古い結果を表示しない。**ただしリクエスト自体は中断しない**（下記）。
- 同じ食材（同じ言語）のリクエストが進行中なら、新たに送らずにその結果を共有する。閉じてすぐ開き直した場合や、開発時の React Strict Mode で effect が2回実行される場合も、backend へのリクエストは1回になる。

**中断しない理由（実装時の変更）:** 当初は `AbortController` で中断する方針だったが、ブラウザ側で中断しても backend は Gemini の呼び出しを続けるため、AI の利用枠を節約できない。むしろ中断すると結果を捨てることになり、同じ食材を開き直したときに再度 Gemini を呼ぶことになる。そのため、進行中のリクエストは最後まで待ち、成功すればキャッシュに入れる（画面には、そのモーダルが開いている場合だけ表示する）。

### 5.2 エラーの種類と表示

| 種類 | 判定 | メッセージ（ja） | 「もう一度試す」 |
| --- | --- | --- | --- |
| 通信失敗 | `fetch` が例外（中断以外） | サーバーに接続できませんでした。通信環境を確認してもう一度お試しください。 | 出す |
| タイムアウト | **20秒**で応答が無い（`AbortSignal.timeout`） | 説明の生成に時間がかかりすぎました。もう一度お試しください。 | 出す |
| 設定エラー | 404 | アプリの設定が正しくありません。管理者にお問い合わせください。 | 出さない |
| 生成失敗 | 500 などその他の非200、または422 | 説明を生成できませんでした。もう一度お試しください。 | 出す |
| 不正な応答 | 200 だが `status` が `"success"` でない、`data.what_is_it` が空でない文字列でない、JSONとして読めない | 説明を生成できませんでした。もう一度お試しください。 | 出す |

補足:

- 422 は、フロントが常に正しい形で送る限り起きない。起きた場合はフロントの不具合なので、ユーザーには「生成失敗」と同じ表示にし、コンソールに記録する。
- `data.made_of` だけが欠けている・空の場合はエラーにせず、「原材料」の見出しを出さずに説明だけ表示する。
- タイムアウトの20秒は、実測（約5〜6秒）の3倍強として置いた暫定値。料理解析（30秒）より短いのは、生成する文章が短いため。
- メッセージは i18n（en/ja/th）で用意する。通信失敗・設定エラーは既存の `capture.confirming.error.*` と同じ文言でよいが、キーはこの機能用に分ける。

## 6. キャッシュ

- 成功した結果を、**`language` と `ingredient` の組**をキーにしてメモリにキャッシュする。同じ食材を再度開いたときは即座に表示し、AIを呼ばない。
- 保存先はメモリのみ（Local Storage には保存しない）。ページの再読み込み・アプリを閉じると消える。
- 理由: AI の呼び出しを減らして費用と待ち時間を抑える。一方で、生成内容は変わりうるうえに料理解析の結果に依存する補足情報なので、長期保存はしない。

## 8. 今回のスコープ外

- アレルギー情報（`allergens`）のチップを押したときの説明表示
- ユーザーが設定したアレルギー（`allergy-selection.md`）と `made_of` の突き合わせ・警告表示
- 生成結果の端末への保存、サーバー側でのキャッシュ
- 食材名の自由入力による検索

## 9. backend への確認・要望

1. **`ingredient` の表記:** 仕様例は英語名（`Katsuobushi (Bonito flakes)`）だが、フロントは表示中の言語の食材名を送る（3.2）。この形で問題ないか確認する。
   A. 問題ない
2. **`language` の検証:** 現状は任意の文字列を受け付け、そのままプロンプトに入る。`en` / `jp` / `th` 以外は422にしてほしい。
3. **プロンプトインジェクション:** `ingredient` がそのままプロンプトに埋め込まれている。フロントから送るのはDB由来の食材名だけだが、APIは誰でも呼べるため、長さの上限（例: 100文字）と、指示文として解釈されないプロンプトの書き方を検討してほしい。
4. **レスポンスの検証:** Gemini の出力のキー・型を検証せずに返しているため、`what_is_it` / `made_of` が揃っていない場合は500にしてほしい（フロントでも検証する）。
5. **エラー詳細:** 500 の `detail` に内部の例外文字列がそのまま入っている。本番では一般的なメッセージにしてほしい（フロントは表示しない）。
6. **利用枠超過の区別:** 対応済み。モデルの自動切り替え（3.6）とあわせて、すべてのモデルが上限に達したときは 429 を返すようになった。フロントで「混み合っています。しばらくしてからお試しください」のような専用メッセージを出すかは未対応（現状は 5.2 の「生成失敗」）。

## 10. 動作確認チェックリスト

- 食材ボタンを押すとモーダルが開き、食材名が即座に表示され、読み込み中の表示が出る
- 数秒後に「どんな食材？」「原材料」と注意書きが表示される
- en / ja / th のそれぞれで、その言語の説明が返る（`ja` は `jp` で送られている）
- 同じ食材を閉じて再度開くと、読み込み中を挟まずに即座に表示される（キャッシュ）
- 閉じるボタン・背景のタップ・Escキーで閉じられ、フォーカスが食材ボタンに戻る
- 読み込み中に閉じてから別の食材を開いても、前の食材の結果が表示されない
- 1回タップするごとに backend へのリクエストは1回（開発時の Strict Mode でも2回にならない）。読み込み中に閉じて同じ食材を開き直しても増えない
- backend を止めた状態で押すと通信失敗のメッセージと「もう一度試す」が出て、backend を起動してから押すと表示される
- `AI_API_ORIGIN` 未設定では設定エラーのメッセージが出る
- エラーが起きても、料理データカードの表示・操作に影響しない
