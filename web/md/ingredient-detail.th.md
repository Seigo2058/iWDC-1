# เอกสารข้อกำหนด: การเชื่อมต่อ API รายละเอียดวัตถุดิบ

> เอกสารนี้แปลจากต้นฉบับภาษาญี่ปุ่น `ingredient-detail.md` หากเนื้อหาไม่ตรงกัน ให้ถือต้นฉบับภาษาญี่ปุ่นเป็นหลัก

**ผลิตภัณฑ์เป้าหมาย:** Point & Know (API รายละเอียดวัตถุดิบ)
**ข้อสมมติฐาน:** `POST /api/ingredient-detail` ของ `ai/app/routers/food.py` (backend พัฒนาแล้ว) ใช้โครงสร้างการเชื่อมต่อของ API วิเคราะห์อาหาร (`connect-aisystem.md`) ตามเดิม

## 1. ความเป็นมาและวัตถุประสงค์

เมื่อผู้ใช้แตะวัตถุดิบที่แสดงใน "ส่วนประกอบหลัก" ของการ์ดข้อมูลอาหาร (`FoodDetail`) ให้แสดงป๊อปอัปว่าวัตถุดิบนั้นคืออะไร (คำอธิบาย) และทำมาจากอะไร (วัตถุดิบตั้งต้น)

เพื่อประหยัดพื้นที่ฐานข้อมูล ฟังก์ชันนี้**ไม่ใช้ฐานข้อมูล แต่ให้ AI (Gemini) สร้างและแปลคำอธิบายทุกครั้งที่มี request** ดังนั้นการตอบสนองจะใช้เวลาหลายวินาที และเนื้อหาอาจไม่เหมือนกันทุกครั้ง

## 2. ตำแหน่งภายในแอป

| หัวข้อ | รายละเอียด |
| --- | --- |
| จังหวะที่เรียก | เมื่อกดปุ่มวัตถุดิบใน "ส่วนประกอบหลัก" ของการ์ดข้อมูลอาหาร |
| ผู้เรียก | `web/lib/ingredient/fetchIngredientDetail.ts` ที่สร้างใหม่ (บทที่ 7) |
| การแสดงผล | modal รายละเอียดวัตถุดิบ (`web/components/capture/IngredientDetailModal.tsx` ที่สร้างใหม่ บทที่ 4) |
| หน้าจอเป้าหมาย | ทั้งการ์ดข้อมูลอาหารเมื่อมี 1 รายการ และการ์ดข้อมูลอาหารที่แตะจากรายการเมื่อมีหลายรายการ (ใช้ `FoodDetail` ร่วมกัน) |
| การบันทึก | ไม่บันทึกในเซิร์ฟเวอร์・Local Storage แคชในหน่วยความจำเฉพาะระหว่างที่เปิดหน้าจอเดิมอยู่ (บทที่ 6) |

### 2.1 โครงสร้างการเชื่อมต่อ

URL ตามข้อกำหนดของ backend คือ `http://localhost:8000/api/ingredient-detail` แต่**เบราว์เซอร์จะไม่เรียกโดยตรง ให้เรียก `/api/ingredient-detail` ใน origin เดียวกันเหมือน API วิเคราะห์อาหาร แล้วส่งต่อไปยัง `AI_API_ORIGIN` ด้วย `rewrites` ใน `next.config.ts`** (เหตุผลเดียวกับ `connect-aisystem.md` 2.1: ใช้ tunnel เส้นเดียวจากสมาร์ทโฟนจริง หลีกเลี่ยง Mixed Content ไม่ได้รับผลกระทบจาก CORS)

```
เบราว์เซอร์ ──POST /api/ingredient-detail──▶ Next.js (web, :3000)
                                              │ rewrites (ส่งต่อไปยัง AI_API_ORIGIN)
                                              ▼
                                     FastAPI (ai, :8000) ──▶ Gemini
```

ปัจจุบัน `rewrites` มีเพียง `/api/analyze-food` จึงต้องเพิ่มการส่งต่อ `/api/ingredient-detail`

## 3. ข้อกำหนด API ที่เชื่อมต่อ

### 3.1 Endpoint

| หัวข้อ | รายละเอียด |
| --- | --- |
| Method | POST |
| URL ที่เรียกจากเบราว์เซอร์ | `/api/ingredient-detail` (origin เดียวกัน, คงที่) |
| ปลายทางที่ส่งต่อ | `${AI_API_ORIGIN}/api/ingredient-detail` |
| Content-Type | `application/json` (ต่างจาก API วิเคราะห์อาหาร ไม่ใช่ FormData) |

### 3.2 Request

```json
{
  "ingredient": "Katsuobushi (Bonito flakes)",
  "language": "jp"
}
```

| ฟิลด์ | ชนิด | จำเป็น | รายละเอียด |
| --- | --- | --- | --- |
| `ingredient` | string | ○ | ชื่อวัตถุดิบที่ผู้ใช้แตะ **ส่งตามที่แสดงบนหน้าจอ (ชื่อวัตถุดิบในภาษาปัจจุบัน)** (เหตุผลด้านล่าง) |
| `language` | `"en"` / `"jp"` / `"th"` | ○ | ภาษาที่เลือกอยู่ในแอปขณะนั้น ตีความ `ja` ของแอปนี้เป็น `jp` (ใช้ `toApiLang()` ที่มีอยู่แล้ว) |

**เหตุผลที่ส่งชื่อตามที่แสดงใน `ingredient`:** อาร์เรย์ของแต่ละภาษาใน `food_items.ingredients` ไม่รับประกันว่าวัตถุดิบเดียวกันจะอยู่ในตำแหน่งเดียวกัน (ภาษาที่ไม่มีคำแปลจะแสดงภาษาอังกฤษแทน) จึงไม่สามารถหาชื่อภาษาอังกฤษจากชื่อที่แตะได้อย่างแน่นอน AI เข้าใจชื่อวัตถุดิบภาษาญี่ปุ่นและภาษาไทยได้ด้วย จากการตรวจสอบเมื่อ 2026-09-13 `"ingredient": "ナンプラー", "language": "th"` ได้คำอธิบายภาษาไทยที่ถูกต้องกลับมา

### 3.3 Response (เมื่อสำเร็จ, สถานะ 200)

```json
{
  "status": "success",
  "data": {
    "what_is_it": "鰹の肉を加熱してから乾燥させた日本の保存食品です。出汁をとったり、トッピングとして使われます。",
    "made_of": "鰹（カツオ）"
  }
}
```

| ฟิลด์ | ชนิด | รายละเอียด |
| --- | --- | --- |
| `status` | `"success"` | แสดงว่าสร้างสำเร็จ backend จะไม่คืนค่า 200 ในกรณีอื่นนอกจากสำเร็จ |
| `data.what_is_it` | string | คำอธิบายสั้น ๆ ของวัตถุดิบ (1〜2 ประโยค) เป็นภาษาที่ระบุใน `language` |
| `data.made_of` | string | สตริงสั้น ๆ ที่ระบุวัตถุดิบตั้งต้น เป็นภาษาที่ระบุใน `language` |

**ข้อควรระวัง:** เนื้อหาใน `data` คือผลลัพธ์ของ Gemini ที่อ่านเป็น JSON โดยตรง backend ไม่ได้ตรวจสอบคีย์หรือชนิดข้อมูล อาจมีคีย์ขาดหายหรือมีค่าที่ไม่ใช่สตริง จึงตรวจสอบที่ frontend (บทที่ 5)

### 3.4 ข้อผิดพลาดที่ backend ส่งกลับ

| สถานะ | เงื่อนไขที่เกิด | body |
| --- | --- | --- |
| 422 | ไม่มี `ingredient` / `language` หรืออ่านเป็น JSON ไม่ได้ (การตรวจสอบของ FastAPI) | `{"detail": [...]}` |
| 429 | โมเดล Gemini ทั้งหมดที่ตั้งค่าไว้ใช้โควตาครบแล้ว (3.6) | `{"detail": "AI request limit reached for all models. ..."}` |
| 503 | โมเดลที่ใช้ได้ทั้งหมดมีผู้ใช้หนาแน่น・ไม่ตอบสนอง (3.6) | `{"detail": "AI models are busy right now. ..."}` |
| 500 | เรียก Gemini ไม่สำเร็จ หรืออ่านผลลัพธ์ของ Gemini เป็น JSON ไม่ได้ | `{"detail": "AI Processing Error: ..."}` |
| 500 | backend ไม่ได้ทำงาน／เข้าถึงไม่ได้ (Next.js ส่งต่อไม่สำเร็จ) | ข้อผิดพลาดของ Next.js |
| 404 | ไม่ได้ตั้งค่า `AI_API_ORIGIN` หรือปลายทางไม่มี `/api/ingredient-detail` | 404 ของ Next.js |

`detail` มีข้อความข้อผิดพลาดภายใน จึง**ไม่แสดงบนหน้าจอ**

### 3.5 เวลาตอบสนอง

ผลการวัดจริงในสภาพแวดล้อมเครื่องเมื่อ 2026-09-13 คือ **ประมาณ 5〜6 วินาที** (เกือบทั้งหมดเป็นเวลาที่ Gemini ใช้สร้าง) ออกแบบ UI โดยสมมติว่าผู้ใช้ต้องรอหลายวินาที (4.3)

### 3.6 โควตาการใช้งาน AI

จากการตรวจสอบเมื่อ 2026-09-13 Gemini API ในโควตาฟรีถูกจำกัดที่ **20 request ต่อวันต่อโมเดล** (`gemini-3.6-flash`) โควตานี้ใช้ร่วมกันระหว่างการวิเคราะห์อาหาร (`/api/analyze-food`) และรายละเอียดวัตถุดิบ

เมื่อโมเดลใดใช้โควตาครบ・มีผู้ใช้หนาแน่น・ไม่ตอบสนองภายใน 12 วินาที backend จะสลับไปยังโมเดลถัดไปโดยอัตโนมัติ (`connect-aisystem.md` 7.1.1) จะคืนค่า **429** (ครบโควตาทั้งหมด) หรือ **503** (มีกรณีผู้ใช้หนาแน่นรวมอยู่ด้วย) เฉพาะเมื่อใช้โมเดลใดไม่ได้เลย และ frontend จะแสดงทั้งสองกรณีเป็น "สร้างไม่สำเร็จ" (5.2) การแคชและการใช้ request ร่วมกันพร้อมกัน (5.1・บทที่ 6) ก็เพื่อประหยัดโควตานี้ด้วย

## 4. ข้อกำหนดหน้าจอ

### 4.1 ปุ่มวัตถุดิบ

- เปลี่ยน chip ใน "ส่วนประกอบหลัก" ของการ์ดข้อมูลอาหาร (ปัจจุบันเป็นเพียงการแสดงผลด้วย `<li>`) ให้เป็นปุ่มที่กดได้ คงรูปลักษณ์ของ chip เดิมไว้ และเพิ่มการเปลี่ยนแปลงพอให้รู้ว่ากดได้ (สีพื้นหลังเมื่อ hover, เคอร์เซอร์)
- เพิ่มคำอธิบาย 1 บรรทัดใต้หัวข้อ "ส่วนประกอบหลัก" ว่า "แตะที่วัตถุดิบเพื่อดูคำอธิบาย"
- chip ของข้อมูลสารก่อภูมิแพ้ (`allergens`) อยู่นอกเป้าหมายครั้งนี้ (ยังกดไม่ได้)

### 4.2 modal รายละเอียดวัตถุดิบ

| องค์ประกอบ | รายละเอียด |
| --- | --- |
| หัวเรื่อง | ชื่อวัตถุดิบที่แตะ (เหมือนกับที่แสดงบนปุ่ม) |
| "วัตถุดิบนี้คืออะไร?" | `data.what_is_it` |
| "ทำมาจาก" | `data.made_of` หากว่างจะไม่แสดงทั้งหัวข้อ |
| ข้อควรระวัง | แสดง "คำอธิบายนี้สร้างโดย AI และอาจไม่ถูกต้อง โปรดอย่าใช้ในการตัดสินใจเรื่องอาการแพ้อาหาร และสอบถามทางร้านทุกครั้ง" เสมอ |
| ปิด | ปิดได้ด้วยปุ่มปิดมุมขวาบน การแตะพื้นหลัง (overlay) หรือปุ่ม Esc อย่างใดอย่างหนึ่ง |

- บนสมาร์ทโฟนแสดงเป็น bottom sheet (แผงที่เลื่อนขึ้นจากด้านล่างของหน้าจอ) บนหน้าจอกว้างแสดงเป็น dialog ตรงกลาง
- ใช้องค์ประกอบ `<dialog>` แบบ native (`showModal()`) ระหว่างที่เปิดอยู่ ผู้ใช้จะใช้งานส่วนด้านหลังไม่ได้ และ focus จะอยู่ภายใน modal เมื่อปิดแล้ว ให้ focus กลับไปที่ปุ่มวัตถุดิบที่กด
- แสดงเนื้อหาเป็นข้อความของ React (ไม่ตีความเป็น HTML)

**เหตุผลที่ต้องมีข้อควรระวัง:** "ทำมาจาก" เป็นข้อมูลที่ผู้ใช้ที่มีอาการแพ้มักใช้ประกอบการตัดสินใจ แต่เป็นผลที่ AI สร้างขึ้น และไม่จำเป็นต้องตรงกับวัตถุดิบที่ใช้ในอาหารจริง

### 4.3 สถานะและการแสดงผล

```
[กดปุ่มวัตถุดิบ] → กำลังโหลด ──สำเร็จ──▶ แสดงคำอธิบาย
                        │
                        └──ล้มเหลว──▶ แสดงข้อผิดพลาด ──[ลองอีกครั้ง]──▶ กำลังโหลด
```

| สถานะ | การแสดงผล |
| --- | --- |
| กำลังโหลด | แสดงหัวเรื่อง (ชื่อวัตถุดิบ) ทันที และแสดง skeleton (แถบสีเทา) กับ "กำลังสร้างคำอธิบาย..." ในตำแหน่งเนื้อหา กดปุ่มปิดได้ |
| สำเร็จ | องค์ประกอบต่าง ๆ ใน 4.2 |
| ล้มเหลว | ข้อความข้อผิดพลาด (บทที่ 5) และปุ่ม "ลองอีกครั้ง" กดปุ่มปิดได้ |

## 5. การจัดการข้อผิดพลาด

### 5.1 แนวทาง

- แสดงข้อผิดพลาด**เฉพาะภายใน modal** ไม่ส่งผลต่อการ์ดข้อมูลอาหารหรือขั้นตอนถ่ายภาพ (รายละเอียดวัตถุดิบเป็นข้อมูลเสริม แม้ล้มเหลวก็ยังดูข้อมูลอาหารได้)
- **ไม่ลองใหม่อัตโนมัติ** เนื่องจากการเรียก AI มีค่าใช้จ่ายและใช้เวลา จะลองใหม่เฉพาะเมื่อผู้ใช้กด "ลองอีกครั้ง"
- **ไม่แคชผลที่ล้มเหลว** (บทที่ 6) เมื่อปิด modal แล้วกดวัตถุดิบเดิมอีกครั้ง จะส่ง request ใหม่
- หากปิด modal ระหว่างโหลด หรือเปิดวัตถุดิบอื่น จะไม่แสดงผลเก่าที่ส่งกลับมาทีหลัง **แต่จะไม่ยกเลิก request** (ด้านล่าง)
- หากมี request ของวัตถุดิบเดียวกัน (ภาษาเดียวกัน) กำลังดำเนินอยู่ จะไม่ส่งใหม่ แต่ใช้ผลลัพธ์นั้นร่วมกัน แม้ปิดแล้วเปิดใหม่ทันที หรือ effect ทำงาน 2 ครั้งจาก React Strict Mode ระหว่างพัฒนา request ไปยัง backend ก็จะมีเพียง 1 ครั้ง

**เหตุผลที่ไม่ยกเลิก (เปลี่ยนแปลงระหว่างการพัฒนา):** เดิมมีแนวทางยกเลิกด้วย `AbortController` แต่แม้ยกเลิกฝั่งเบราว์เซอร์ backend ก็ยังเรียก Gemini ต่อไป จึงไม่ช่วยประหยัดโควตา AI กลับกัน การยกเลิกทำให้ต้องทิ้งผลลัพธ์ และต้องเรียก Gemini อีกครั้งเมื่อเปิดวัตถุดิบเดิมใหม่ ดังนั้นจึงรอ request ที่กำลังดำเนินอยู่จนเสร็จ และหากสำเร็จจะเก็บลงแคช (แสดงบนหน้าจอเฉพาะเมื่อ modal นั้นยังเปิดอยู่)

### 5.2 ชนิดของข้อผิดพลาดและการแสดงผล

| ชนิด | การตัดสิน | ข้อความ (th) | "ลองอีกครั้ง" |
| --- | --- | --- | --- |
| การสื่อสารล้มเหลว | `fetch` เกิด exception (ที่ไม่ใช่การยกเลิก) | เชื่อมต่อเซิร์ฟเวอร์ไม่ได้ กรุณาตรวจสอบการเชื่อมต่อแล้วลองอีกครั้ง | แสดง |
| Timeout | ไม่มีการตอบสนองภายใน **20 วินาที** (`AbortSignal.timeout`) | การสร้างคำอธิบายใช้เวลานานเกินไป กรุณาลองอีกครั้ง | แสดง |
| ข้อผิดพลาดการตั้งค่า | 404 | แอปตั้งค่าไม่ถูกต้อง กรุณาติดต่อผู้ดูแลระบบ | ไม่แสดง |
| สร้างไม่สำเร็จ | ไม่ใช่ 200 กรณีอื่น เช่น 500 หรือ 422 | ไม่สามารถสร้างคำอธิบายได้ กรุณาลองอีกครั้ง | แสดง |
| Response ไม่ถูกต้อง | 200 แต่ `status` ไม่ใช่ `"success"`, `data.what_is_it` ไม่ใช่สตริงที่ไม่ว่าง หรืออ่านเป็น JSON ไม่ได้ | ไม่สามารถสร้างคำอธิบายได้ กรุณาลองอีกครั้ง | แสดง |

หมายเหตุ:

- 422 จะไม่เกิดขึ้นตราบใดที่ frontend ส่งรูปแบบที่ถูกต้องเสมอ หากเกิดขึ้นถือเป็นข้อบกพร่องของ frontend จะแสดงต่อผู้ใช้เหมือน "สร้างไม่สำเร็จ" และบันทึกลงใน console
- หากขาดเพียง `data.made_of` หรือเป็นค่าว่าง จะไม่ถือเป็นข้อผิดพลาด โดยแสดงเฉพาะคำอธิบายและไม่แสดงหัวข้อ "ทำมาจาก"
- timeout 20 วินาทีเป็นค่าชั่วคราวที่ตั้งไว้มากกว่า 3 เท่าของผลการวัดจริง (ประมาณ 5〜6 วินาที) สั้นกว่าการวิเคราะห์อาหาร (30 วินาที) เพราะข้อความที่สร้างสั้นกว่า
- ข้อความเตรียมไว้ด้วย i18n (en/ja/th) การสื่อสารล้มเหลว・ข้อผิดพลาดการตั้งค่าใช้ถ้อยคำเดียวกับ `capture.confirming.error.*` ที่มีอยู่แล้วได้ แต่แยกคีย์สำหรับฟังก์ชันนี้

## 6. แคช

- แคชผลที่สำเร็จไว้ในหน่วยความจำ โดยใช้**คู่ของ `language` และ `ingredient`** เป็นคีย์ เมื่อเปิดวัตถุดิบเดิมอีกครั้ง จะแสดงทันทีโดยไม่เรียก AI
- บันทึกในหน่วยความจำเท่านั้น (ไม่บันทึกใน Local Storage) จะหายไปเมื่อโหลดหน้าใหม่・ปิดแอป
- เหตุผล: ลดการเรียก AI เพื่อลดค่าใช้จ่ายและเวลารอ ในขณะเดียวกัน เนื้อหาที่สร้างอาจเปลี่ยนแปลงได้ และเป็นข้อมูลเสริมที่ขึ้นกับผลการวิเคราะห์อาหาร จึงไม่เก็บไว้ระยะยาว

## 8. นอกขอบเขตในครั้งนี้

- การแสดงคำอธิบายเมื่อกด chip ของข้อมูลสารก่อภูมิแพ้ (`allergens`)
- การเปรียบเทียบอาการแพ้ที่ผู้ใช้ตั้งค่าไว้ (`allergy-selection.md`) กับ `made_of`・การแสดงคำเตือน
- การบันทึกผลที่สร้างลงในอุปกรณ์ การแคชฝั่งเซิร์ฟเวอร์
- การค้นหาด้วยการพิมพ์ชื่อวัตถุดิบเอง

## 9. ประเด็นที่ต้องยืนยัน・ข้อเสนอถึง backend

1. **รูปแบบของ `ingredient`:** ตัวอย่างในข้อกำหนดเป็นชื่อภาษาอังกฤษ (`Katsuobushi (Bonito flakes)`) แต่ frontend ส่งชื่อวัตถุดิบในภาษาที่แสดงอยู่ (3.2) ตรวจสอบว่ารูปแบบนี้ไม่มีปัญหาหรือไม่
   A. ไม่มีปัญหา
2. **การตรวจสอบ `language`:** ปัจจุบันรับสตริงใดก็ได้และใส่ลงใน prompt โดยตรง ขอให้คืนค่า 422 สำหรับค่าที่ไม่ใช่ `en` / `jp` / `th`
3. **Prompt injection:** `ingredient` ถูกฝังลงใน prompt โดยตรง แม้ frontend จะส่งเฉพาะชื่อวัตถุดิบจาก DB แต่ใครก็เรียก API ได้ ขอให้พิจารณากำหนดความยาวสูงสุด (ตัวอย่าง: 100 ตัวอักษร) และวิธีเขียน prompt ที่ไม่ถูกตีความเป็นคำสั่ง
4. **การตรวจสอบ response:** ส่งผลลัพธ์ของ Gemini กลับไปโดยไม่ตรวจสอบคีย์・ชนิดข้อมูล ขอให้คืนค่า 500 เมื่อ `what_is_it` / `made_of` ไม่ครบ (frontend ก็ตรวจสอบด้วย)
5. **รายละเอียดข้อผิดพลาด:** `detail` ของ 500 มีข้อความ exception ภายในอยู่ตามเดิม ขอให้ใช้ข้อความทั่วไปใน production (frontend ไม่แสดง)
6. **การแยกแยะการใช้โควตาเกิน:** ดำเนินการแล้ว ร่วมกับการสลับโมเดลอัตโนมัติ (3.6) เมื่อโมเดลทั้งหมดใช้โควตาครบ จะคืนค่า 429 ส่วนการแสดงข้อความเฉพาะที่ frontend เช่น "มีผู้ใช้งานจำนวนมาก กรุณาลองใหม่ภายหลัง" ยังไม่ได้ดำเนินการ (ปัจจุบันแสดงเป็น "สร้างไม่สำเร็จ" ตาม 5.2)

## 10. รายการตรวจสอบการทำงาน

- เมื่อกดปุ่มวัตถุดิบ modal จะเปิด แสดงชื่อวัตถุดิบทันที และแสดงสถานะกำลังโหลด
- หลังจากหลายวินาที จะแสดง "วัตถุดิบนี้คืออะไร?" "ทำมาจาก" และข้อควรระวัง
- ใน en / ja / th แต่ละภาษา จะได้คำอธิบายในภาษานั้น (`ja` ถูกส่งเป็น `jp`)
- เมื่อปิดแล้วเปิดวัตถุดิบเดิมอีกครั้ง จะแสดงทันทีโดยไม่ผ่านสถานะกำลังโหลด (แคช)
- ปิดได้ด้วยปุ่มปิด・การแตะพื้นหลัง・ปุ่ม Esc และ focus กลับไปที่ปุ่มวัตถุดิบ
- แม้ปิดระหว่างโหลดแล้วเปิดวัตถุดิบอื่น ผลของวัตถุดิบก่อนหน้าจะไม่แสดง
- ทุกครั้งที่แตะ 1 ครั้ง จะมี request ไปยัง backend 1 ครั้ง (ไม่เป็น 2 ครั้งแม้ใน Strict Mode ระหว่างพัฒนา) และไม่เพิ่มขึ้นแม้ปิดระหว่างโหลดแล้วเปิดวัตถุดิบเดิมใหม่
- เมื่อกดขณะหยุด backend จะแสดงข้อความการสื่อสารล้มเหลวและ "ลองอีกครั้ง" และเมื่อเริ่ม backend แล้วกดอีกครั้งจะแสดงผล
- เมื่อไม่ได้ตั้งค่า `AI_API_ORIGIN` จะแสดงข้อความข้อผิดพลาดการตั้งค่า
- แม้เกิดข้อผิดพลาด ก็ไม่ส่งผลต่อการแสดงผล・การใช้งานการ์ดข้อมูลอาหาร
