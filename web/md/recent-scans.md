# 最近のスキャン履歴（Recent Scan）要件定義書

**対象プロダクト:** Point & Know（ホーム画面）
**前提:** 料理解析API（`connect-aisystem.md`）、料理データカード（`FoodDetail`）、食材詳細（`ingredient-detail.md`）は実装済み。
**改訂:** 10章の確認事項への回答と、その後の追加指示（th の時刻を24時間表記に戻す、3言語の料理名と写真の URL も保存する）を反映（2026-09-14）。さらに追加指示で、**スキャンした時点で結果の料理をまとめて1件として保存し、複数品のスキャンはホーム画面で専用のイラストと「OOなど」で表示する**形に変更（2026-09-14）。

## 1. 背景・目的

スキャン（撮影して解析）した料理を、ホーム画面からもう一度見られるようにする。スキャンした時点で、見つかった料理をまとめて1件の履歴として端末の Local Storage に記録し、ホーム画面の「Recent Scan」に新しい順でカード表示する。1品のスキャンはその料理の詳細を、複数品のスキャンはその回の料理一覧を開き、料理の詳細はデータベースから最新の情報を取得して料理データカードで表示する。

履歴はこの端末・ブラウザだけに保存し、サーバーやアカウントには送信しない（`allergy-selection.md` と同じ方針）。

## 2. アプリ内の位置づけ

| 項目 | 内容 |
| --- | --- |
| 保存するタイミング | 料理解析が成功した時点。見つかった料理をまとめて1件として保存する（3.1） |
| 保存する内容 | スキャン1回ごとに、ID・スキャン日時・料理の一覧（各料理の ID・3言語の料理名・写真の URL）（3.2） |
| 保存先 | ブラウザの Local Storage のみ（サーバー送信なし） |
| 表示場所 | ホーム画面（`/[lang]`）の「Recent Scan」セクション。1品のスキャンは料理の写真と名前、複数品のスキャンは専用のイラストと「OOなど」。カードは保存した内容だけで表示し、DBは参照しない（4章） |
| カードを押したとき | 1品: 料理詳細ページ（`/[lang]/foods/[foodId]`、4.4）。複数品: そのスキャンの料理一覧ページ（`/[lang]/scans/[scanId]`、4.5）から各料理の詳細へ |
| 必要な backend の追加 | 料理を ID で1件取得するAPI（`GET /api/foods/{food_id}`、5章）。現状の backend には料理を画像以外から取得する手段が無い |

## 3. 保存仕様

### 3.1 保存するタイミング

**スキャンした時点で、見つかった料理をまとめて1件として**保存する。

| 状況 | 保存 |
| --- | --- |
| 料理解析が `status: "success"`（1品） | **する**。その1品を1件として保存 |
| 料理解析が `status: "success"`（複数品） | **する**。見つかった全品を1件にまとめて保存（一覧から料理を開いたかどうかは関係ない） |
| 結果画面・複数品の一覧から料理データカードを開いた | しない（保存はスキャンした時点で済んでいる） |
| `partial_success`（識別できたがDBに無い）／`fail`（識別できない）／エラー | しない（DBに情報が無く、あとから開けないため） |
| 「Recent Scan」のカード・料理一覧から料理詳細を開いた | しない（新しいスキャンではないため、順番も変えない） |

保存処理は解析結果をストアに入れる箇所（`web/lib/capture/runAnalysis.ts` の成功時）で1回だけ行い、コンポーネントの表示（`useEffect`）では行わない（開発時の React Strict Mode で2回実行されるため）。

**スキャン日時**は**解析が成功した時刻**とする。

### 3.2 保存する内容

スキャン1回を1件とし、その回に見つかった料理の一覧を持たせる。値はすべて解析結果（料理解析APIの `data[]`）から取る。

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `id` | string | スキャンごとの ID（端末内で一意）。料理一覧ページの URL に使う |
| `scannedAt` | string | スキャンした日時（ISO 8601、例: `2026-09-14T09:05:00.000Z`） |
| `foods` | 配列 | その回に見つかった料理（解析結果の並び順）。1品以上 |
| `foods[].foodId` | number | `food_items.food_id`。料理詳細を開くときの取得キー |
| `foods[].nameEn` / `nameTh` / `nameJp` | string | 3言語の料理名（`food_items.name_en` / `name_th` / `name_jp`）。現在の表示言語の名前を出す |
| `foods[].descriptionEn` / `descriptionTh` / `descriptionJp` | string | 3言語の料理の説明文（`food_items.description`）。料理一覧ページ（4.5）のカードに現在の表示言語の説明文を出す（空なら英語）。説明文が無い料理は `""`。この項目が無い履歴（説明文を保存する前の履歴）は、4.5 の表示時に一度だけDBから取得して書き足す |
| `foods[].imageUrl` | string \| null | DBの参考写真の URL（`food_items.image_url`）。空なら `null` |

```json
[
  {
    "id": "mu121tek-70p7b4",
    "scannedAt": "2026-09-14T09:43:00.000Z",
    "foods": [
      { "foodId": 1, "nameEn": "Pad Thai", "nameTh": "ผัดไทย", "nameJp": "パッタイ", "descriptionEn": "A famous Thai stir-fried rice noodle dish...", "descriptionTh": "...", "descriptionJp": "...", "imageUrl": "https://..." },
      { "foodId": 2, "nameEn": "Tom Yum Goong", "nameTh": "ต้มยำกุ้ง", "nameJp": "トムヤムクン", "descriptionEn": "...", "descriptionTh": "...", "descriptionJp": "...", "imageUrl": "https://..." }
    ]
  },
  {
    "id": "mu11z2qa-k3x9fd",
    "scannedAt": "2026-09-14T09:05:00.000Z",
    "foods": [
      { "foodId": 7, "nameEn": "Khao Soi", "nameTh": "ข้าวซอย", "nameJp": "カオソーイ", "imageUrl": "https://..." }
    ]
  }
]
```

- **以前の形式との互換:** まとめて保存する前の形式（1件＝料理1品で、`foodId` などが直接並ぶ）の履歴は、読み込み時に1品のスキャンとして扱う。既存の履歴は消えない。

- 料理名と写真の URL はスキャン時点の写し。DBで変わっても、同じ料理をもう一度保存するまでカードの表示は変わらない（カードを押したときの詳細はDBから最新を取得する。4.4）。
- **カードの写真はDBの参考写真**を使う。ユーザーが撮った写真は保存しない（Blob は Local Storage に保存できず、画像を文字列にすると容量を圧迫する。複数品のときはメニュー全体の写真で、料理ごとの写真にならない）。
- 写真そのものではなく URL だけを保存するため、写真は表示のたびに外部サイトから読み込む。通信できない環境では写真だけが代替アイコンになる（6.1）。

### 3.3 並び順・重複・件数

- 配列の先頭が最新。ホーム画面では**左から新しい順**に並べる。保存するたびに先頭に入れる。
- **1品のスキャンで同じ料理をもう一度スキャンしたら、古い1品のスキャンを消して新しい記録を先頭に入れる**（1件にまとめる）。
- **複数品のスキャンは、毎回別の1件として残す**（組み合わせが同じでもまとめない）。1品のスキャンで、複数品のスキャンに含まれる料理を撮っても、複数品の記録は消さない。
- **最大20件**（スキャン20回分）。超えたら古いものから消す（1件あたり数百バイト〜数KBのため、容量の心配は無い）。

### 3.4 Local Storage

- キー: `recentScans`。値は 3.2 の配列の JSON 文字列。
- 読み込み時に形を検証し、壊れた料理（`foodId` が整数でない、`nameEn` が空でない文字列でない）は捨て、有効な料理が1品も無いスキャンや、`id` が無い・`scannedAt` が日付として読めないスキャンも捨てる。`nameTh` / `nameJp` が欠けている・空の場合は捨てずに `nameEn` で代用する。`imageUrl` が文字列でない場合は `null`（代替アイコン）として扱う。JSON として読めない場合は空の履歴として扱う。
- Local Storage はサーバー側描画（SSR）では使えないため、アレルギー設定ページと同じく `useSyncExternalStore` で読み、描画の食い違い（hydration mismatch）を起こさない。

## 4. 画面仕様

### 4.1 ホーム画面の「Recent Scan」セクション

- ホーム画面の「Start scanning」「My Allergies」のカードの下に「Recent Scan」セクションを置く。**履歴が0件でも常に表示する。**
- 見出しは時計アイコン＋表示言語の見出し（en: `Recent Scans` / ja: `最近のスキャン` / th: `สแกนล่าสุด`）。en は当初 `Recent Scan` だったが、Figma のホーム画面デザインに合わせて `Recent Scans` にした。
- カードを**横一列**に並べ、左端が最新。画面に入りきらない分は横スクロールで見る（スクロールはセクション内だけで、ページ全体は横にスクロールさせない）。カードの列は画面の右端まで伸ばし、1枚目は他のカードの左端に揃える。スクロール時はカード単位で止まる（scroll snap）。
- 列の下中央に、デザインどおりの小さなスクロール位置の表示（灰色のバー）を出す。カードが画面に収まっているときは出さない。
- 見た目は Figma のホーム画面デザインに従う（スマホ: `Home`、PC: `MacBook Pro 16' - 1`。幅 1280px 以上で PC のサイズに切り替える）。
- カードは Local Storage の内容だけで表示し、**ホーム画面ではAPIを呼ばない**（写真の画像の読み込みを除く）。

**履歴が0件のとき**は、通常のカードと同じ大きさの**空のカードを1枚**表示し、`No Recent Scan` と表示する（ja: `スキャン履歴はありません` / th: `ยังไม่มีประวัติการสแกน`）。

- 枠は点線、写真の位置には料理アイコン（`lucide-react`）を薄く出す。
- 押せない（ボタン・リンクにしない）。

### 4.2 カード

| 要素 | 1品のスキャン | 複数品のスキャン |
| --- | --- | --- |
| 画像 | 保存した `imageUrl` の画像を横長（209:122、デザインどおり）に切り抜いて表示。URL が無い、または読み込みに失敗したときは、灰色の背景に料理アイコン（`lucide-react`）を出す | 複数の料理が含まれることを示す**専用のイラスト**（お皿3枚が重なった SVG、`MultiDishIllustration`）。読み上げ用の名前は「複数の料理」 |
| 料理名 | 保存した、現在の表示言語の名前（ja は `nameJp`、th は `nameTh`、en は `nameEn`。空なら `nameEn`）。2行を超えたら省略 | 1品目（解析結果の並び順の先頭）の名前を使い、**「OOなど」**（ja: `パッタイなど` / en: `Pad Thai and more` / th: `ผัดไทย และอื่นๆ`） |
| スキャン日時 | 「相対日＋時刻」（4.3）。例: `今日 午前09:05` | 同左 |
| 押したとき | 料理詳細ページ（4.4） | 料理一覧ページ（4.5） |

- カード全体を1つのリンクにする。幅はデザインどおり固定する（スマホ 240px、PC 442px）。
- 写真は外部サイトの画像なので、Next.js の画像最適化は使わず `<img>` で表示する（既存の参考写真と同じ扱い）。

### 4.3 スキャン日時の表示形式

**相対日**は、端末のタイムゾーンで**暦の日付**の差を数える（24時間単位ではない。例: 昨日の 23:50 にスキャンし、今日の 00:10 に見たら「昨日」）。

| 日付の差 | ja | en | th |
| --- | --- | --- | --- |
| 0 | 今日 | Today | วันนี้ |
| 1 | 昨日 | Yesterday | เมื่อวาน |
| 2 以上 | {n}日前（例: 2日前、30日前） | {n} days ago | {n} วันที่แล้ว |

- 2日前も「一昨日」とは表示せず「2日前」とする（指示どおり「今日・昨日・○日前」の3種類）。そのため `Intl.RelativeTimeFormat` は使わない（ja で「一昨日」、th で「เมื่อวานซืน」になるため）。i18n のキーで用意する。
- 上限は設けない（何日前でも「○日前」）。
- 端末の時計がずれていて未来の日時になった場合は「今日」とする。

**時刻**は、ja は指示どおり「午前00:00」の形式にする。`Intl.DateTimeFormat` で次の設定を使う（2026-09-14 に出力を確認済み）。

| 言語 | 設定 | 0:05 | 9:05 | 12:30 | 21:45 |
| --- | --- | --- | --- | --- | --- |
| ja | `ja-JP`、時・分を2桁、`hourCycle: "h11"` | 午前00:05 | 午前09:05 | 午後00:30 | 午後09:45 |
| en | `en-US`、`hourCycle: "h12"` | 12:05 AM | 9:05 AM | 12:30 PM | 9:45 PM |
| th | `th-TH`、24時間表記＋「น.」 | 00:05 น. | 09:05 น. | 12:30 น. | 21:45 น. |

- ja の `h11` は、正午を「午後00:30」、深夜0時を「午前00:05」と表す日本の慣習に合わせるため。
- th は午前/午後の12時間表記が一般的でなく、`th-TH` の12時間表記は英語の AM/PM になってしまうため、タイで一般的な24時間表記にする。

相対日と時刻の間は、ja・th は半角スペース、en は Figma のデザインに合わせて「, 」（カンマ＋スペース）で区切る。

表示例: `今日 午前09:05` ／ `昨日 午後09:45` ／ `3日前 午後00:30`（en: `Today, 9:05 AM`、th: `วันนี้ 09:05 น.`）

相対日はホーム画面を表示するたびに計算し直す（ホーム画面を開いたまま日付をまたいでも自動では更新しない）。

### 4.4 カードを押したとき（料理詳細ページ）

- `/[lang]/foods/[foodId]` に移動し、`GET /api/foods/{food_id}`（5章）でDBから最新の情報を取得して、結果画面と同じ料理データカード（`FoodDetail`）で表示する。食材をタップしたときの食材詳細（`ingredient-detail.md`）もそのまま使える。
- ユーザーが撮った写真は保存していないため表示しない（DBの参考写真は表示される）。
- 画面上部に「ホームに戻る」を置く。
- この表示では履歴を保存しない・並び順も変えない（3.1）。

| 状態 | 表示 |
| --- | --- |
| 読み込み中 | 履歴に保存した料理名を見出しに即座に表示し、本文の位置に「料理情報を読み込んでいます...」とスケルトンを出す（履歴に無い `foodId` の URL を直接開いた場合は、見出しもスケルトン） |
| 成功 | 料理データカード |
| 失敗 | 6.2 |

### 4.5 複数品のスキャンの料理一覧ページ

- 複数品のカードを押すと `/[lang]/scans/[scanId]` に移動し、そのスキャンで見つかった料理を一覧で表示する。
- 見た目は、撮影直後に複数の料理が見つかったときの一覧と同じデザインにする（Figma: スマホ `Information`（408:3298）/ PC `MacBook Pro 16' - 10`（501:5813）。共通部品 `DishCardList`）。
- カードは Local Storage の履歴（料理名・説明文・写真、3.2）だけで表示し、APIは呼ばない。
- 例外として、説明文を保存する前の履歴（`descriptionEn` などが無い料理）だけは、その料理を `GET /api/foods/{food_id}`（DB参照のみ、AIは使わない）で一度だけ取得し、説明文を履歴に書き足す（取得中は薄い仮の線、取得できなかったときは説明文なし）。書き足した後は再び取得しない。

| 要素 | 内容 |
| --- | --- |
| 見出し | 「見つかった料理 (3)」（en: `Detected Foods (3)` / th: `อาหารที่พบ (3)`）、その下にスキャン日時（4.3）と「料理の情報をチェックしましょう。」 |
| カード | 参考写真（4.2 と同じ代替表示）・料理名・説明文。スマホは1列、PCは2列。押すとその料理の料理詳細ページ（4.4）。URL に一覧のスキャンID（`?scan=<scanId>`）を付けて開く |
| 戻る | 画面下に固定したグレーの「戻る」ボタン。開いたときの画面（通常はホーム）に戻る。直接開いたときはホームへ |
| 履歴に無い `scanId` | エラー画面（404「スキャン履歴が見つかりません」）。削除された、別の端末の URL を開いた等 |

- 一覧から開いた料理詳細ページには、「ホーム」の横に「戻る」ボタンを表示し、押すとこの一覧に戻る（`?scan` が付いているときだけ。ブラウザの「戻る」でも戻れる）。

## 5. 新規API（backend）

### 5.1 エンドポイント

| 項目 | 内容 |
| --- | --- |
| メソッド | GET |
| ブラウザから呼ぶURL | `/api/foods/{food_id}`（同一オリジン。`next.config.ts` の `rewrites` に `/api/foods/:foodId` → `${AI_API_ORIGIN}/api/foods/:foodId` を追加） |
| backend の実装場所 | `ai/app/routers/food.py` |
| 処理 | `food_items` を `food_id` で1件取得して返す。**Gemini を使わないため、AI の利用枠を消費しない** |
| 使う場所 | 料理詳細ページ（4.4）だけ。ホーム画面のカードは保存した内容で表示するため、このAPIを呼ばない |

### 5.2 レスポンス

見つかった場合（200）: `data` の中身は、料理解析API（`connect-aisystem.md` 3.3）の `data[]` の1要素と**同じ形**にする。web 側は解析結果と同じ変換処理（`submitPhoto.ts` の `toFoodData`）で読めるよう、共通化して使う。

```json
{
  "status": "success",
  "data": {
    "food_id": 1,
    "name_en": "Pad Thai",
    "name_th": "ผัดไทย",
    "name_jp": "パッタイ",
    "description": { "en": "...", "th": "...", "jp": "..." },
    "ingredients": { "en": ["..."], "th": ["..."], "jp": ["..."] },
    "allergens": { "en": ["..."], "th": ["..."], "jp": ["..."] },
    "spicy_level": "Low Spicy",
    "calories": 550,
    "protein": 22,
    "carbs": 72,
    "fat": 20,
    "how_to_eat": { "en": "...", "th": "...", "jp": "..." },
    "source_url": "https://...",
    "image_url": "https://..."
  }
}
```

見つからなかった場合（200）: 料理解析APIの未検出（`connect-aisystem.md` 3.4）と同じく、HTTP 200 のまま `status` で表す。

```json
{ "status": "not_found", "data": null }
```

**404 を使わない理由:** web 側では 404 を「`AI_API_ORIGIN` が未設定、または中継先にAPIが無い」設定エラーとして扱っている（`connect-aisystem.md` 3.5）。料理が無い場合まで 404 にすると、2つを区別できなくなる。

| ステータス | 意味 |
| --- | --- |
| 200 `success` | 料理が見つかった |
| 200 `not_found` | その `food_id` の料理がDBに無い（削除された等） |
| 422 | `food_id` が整数でない（FastAPI の検証） |
| 500 | DBエラー、または backend が起動していない（Next.js の中継失敗） |
| 404 | `AI_API_ORIGIN` が未設定、または中継先にこのAPIが無い（設定エラー） |

### 5.3 `allergens` について

このAPIは `allergens` を含めて返す。現在の料理解析API（`/api/analyze-food`）は、複数品対応の改修（コミット `9345172`）で `allergens` が返らなくなっている（2026-09-14 時点の `ai/app/routers/food.py` で確認）。そのままだと、同じ料理でも「スキャン直後の結果」にはアレルギー情報が出ず、「履歴から開いた詳細」には出る、という食い違いになるため、料理解析APIにも `allergens` を戻す（`food_list_data` の辞書に1行追加）。

## 6. エラー処理

### 6.1 ホーム画面のカード

ホーム画面ではAPIを呼ばないため、通信のエラーは起きない。

- 写真の画像が読み込めない（通信できない、URL のリンク切れ等）ときは、そのカードの写真だけ代替アイコンにする。料理名と日時は表示し、カードは押せる。
- DBから料理が削除されていても、ホーム画面では分からない。カードを押して料理詳細ページで「見つからない」と分かったときに、履歴から削除する（6.2）。

### 6.2 料理詳細ページ

エラーは料理詳細ページの中だけで表示する。

| 種類 | 判定 | 表示 | 再試行 |
| --- | --- | --- | --- |
| 料理が無い | 200 `not_found` | 「この料理の情報が見つかりませんでした」。**すべてのスキャンからこの料理を削除し、料理が1品も残らないスキャンは履歴から消す**（二度と開けないため） | なし（「ホームに戻る」のみ） |
| 通信失敗 | `fetch` が例外 | 既存の通信失敗メッセージ | 「もう一度試す」 |
| タイムアウト | **10秒**で応答なし | 「読み込みに時間がかかりすぎました」 | 「もう一度試す」 |
| 設定エラー | 404 | 既存の設定エラーメッセージ | なし |
| 取得失敗 | 500 など、その他の非200。200 でも形が正しくない | 「料理情報を読み込めませんでした」 | 「もう一度試す」 |

- タイムアウトの10秒は、DBを1件引くだけで AI を使わないため、料理解析（30秒）・食材詳細（20秒）より短くした暫定値。

### 10.2 回答から判断した点（新たな確認事項）

回答・追加指示を反映するうえで判断した点。問題なければこのまま実装する。

1. **ホーム画面ではDBを参照しない（追加指示から）:** 料理名と写真の URL を保存するため、カードは保存した内容だけで表示できる。前版で追加した複数件取得のAPI（`GET /api/foods?ids=...`）は不要になったため追加しない。
2. **通信できないときのカード:** 料理名と日時は表示でき、写真だけが代替アイコンになる（6.1）。
3. **複数品のスキャンの扱い（まとめて保存する追加指示から）:** 「OOなど」の OO には解析結果の並び順で1品目の料理名を使う。同じ組み合わせの複数品スキャンでもまとめず、毎回別の1件として残す。複数品のカードを押したときは、そのスキャンの料理一覧ページを新設して表示する（3.3・4.2・4.5）。
4. **「No Recent Scan」の翻訳（回答6・7から）:** 見出しと同じく ja・th は翻訳する（`スキャン履歴はありません` / `ยังไม่มีประวัติการสแกน`）。全言語で「No Recent Scan」にする案もある（4.1）。
5. **回答9の解釈:** 履歴から削除するのは、料理詳細ページを個別に開いて「見つからない」と分かったときだけ。ホーム画面ではDBを参照しないため、削除された料理もカードは通常どおり表示される（6.1・6.2）。
6. **保存した内容の更新（追加指示から）:** カードの料理名・写真の URL はスキャン時点の写しで、DBで変わっても、同じ料理をもう一度保存するまで書き換えない（3.2）。

## 11. 動作確認チェックリスト

- 1品のスキャンで結果が表示されると、ホーム画面の「Recent Scan」の左端にその料理の写真と名前のカードが出る
- 複数品のスキャンでは、結果が表示された時点で（料理を開かなくても）全品が1件として保存され、ホーム画面の左端に専用のイラストと「OOなど」（1品目の名前）のカードが出る
- 複数品のカードを押すと、そのスキャンの料理一覧ページが開き、料理を押すと料理詳細ページが開く。「戻る」で一覧に戻れる
- 同じ料理を1品のスキャンでもう一度スキャンすると、カードが1枚のまま左端に移り、日時が更新される。複数品のスキャンは毎回別のカードになる
- 21件目を保存すると、いちばん古いカードが消える
- `partial_success`・`fail`・エラーのときは履歴が増えない
- Local Storage には、スキャンごとに `id`・`scannedAt`・`foods`（`foodId`・`nameEn`・`nameTh`・`nameJp`・`imageUrl`）だけが保存されている
- まとめて保存する前の形式の履歴が残っていても、1品のカードとして表示される
- 履歴に無い `scanId` の料理一覧ページを開くと「このスキャン履歴は見つかりませんでした。」が表示される
- ホーム画面を開いたとき、APIへのリクエストが発生しない（写真の画像の読み込みを除く）
- カードの日時が、今日・昨日・○日前（2日前も「2日前」）と時刻（ja: `午前09:05`、en: `9:05 AM`（相対日との間はカンマ）、th: `09:05 น.`）で表示される。日付をまたいだ直後でも暦の日付で数えられている
- 表示言語を切り替えると、料理名・日時の表記がその言語になる
- 写真が無い・読み込めない料理は、代替のアイコンが表示される
- 履歴が0件のときは、点線の空のカードに「No Recent Scan」（ja・th は翻訳）が表示され、押せない
- 通信できない状態でホーム画面を開いても、料理名と日時は表示される
- カードを押すと料理詳細ページが開き、DBの最新情報が料理データカードで表示される。食材をタップすると食材詳細が開く
- 料理詳細ページを開いても、履歴の順番は変わらない
- DBに無い `food_id` の料理を開くと「見つかりませんでした」が表示され、その料理がすべてのスキャンから消える（料理が残らないスキャンはカードごと消える）
- ページを再読み込みしても履歴が残り、サーバーには送信されていない
- ホーム画面を再読み込みしても hydration のエラーがコンソールに出ない
